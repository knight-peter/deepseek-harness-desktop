# dsh-desktop 发布总结

> 面向发版操作者。看完本文应能独立完成一次发版：从版本号累加、CI 构建、mac 双架构合并、到 GitCode 国内镜像。详细决策历史见 `docs/plans/国内发布与多更新源方案.md`（含 P1 实测、风险清单、已废弃方案）；本文只保留「当前怎么做」与踩坑结论。

## 1. 发布架构：GitHub 唯一构建源 + 双分发源

```
              GitHub Actions（唯一构建源：免费 macOS runner）
                        │ tag 推送触发
                        ▼
              GitHub Releases（官方分发 + 默认更新源）
                        │ 本机同步
                        ▼
              GitCode Releases（国内镜像 + 国内更新源，固定 latest release）
```

- **构建只能在 GitHub Actions**：国内免费 CI 无 macOS runner，mac arm64 包必须 GitHub 出（已调研，见方案文档 §4）。
- **GitHub Releases**：官方分发，electron-updater 默认更新源（`electron-builder.yml` 的 `publish`）。
- **GitCode 镜像**：`https://gitcode.com/{owner}/{repo}/releases/download/latest/` 固定 `latest` release——URL 跨版本不变，electron-updater 的 generic provider 只需配一次，发版只替换附件。国内用户直连 GitCode CDN（P1 实测 ~5.8MB/s）。
- **应用内选源**（`src/main/updateSources.ts`）：`auto` 先探测 GitCode（2.5s 超时）→ 可达则用，否则 GitHub；失败自动降级重试；管理窗口可固定源。

## 2. 发布命令总览

| 命令 | 脚本 | 作用 | 运行环境 |
|---|---|---|---|
| `pnpm run release-all` | `release-all.mjs` | **一键全流程**：bump → 等 CI → 等 draft → 本机构建（Intel）→ 发布（合并 x64）→ 下载 → GitCode 镜像 | 本机（需 gh + GitHub/GitCode 凭据） |
| `pnpm run release` | `bump-version.mjs` | 累加版本 → commit → tag → push（触发 CI） | 本机 |
| `pnpm run publish-release` | `publish-release.mjs` | 默认仅把 draft 发布为公开；`--with-x64`（Intel 本机）补发 x64 并合并 | 本机 |
| `pnpm run download-release` | `download-release.mjs` | 用 gh CLI 下载 GitHub release 产物到 `release/mirror/`；`--skip mac-x64 / mac-arm64 / win / linux`（可重复）复用本机已构建平台的产物（本地复制、不重复下载，本地文件缺失即报错），不传则全量下载；下载/复制后自动清理非当前版本的旧残留 | 本机（需 gh） |
| `pnpm run sync-domestic` | `sync-domestic.mjs` | 上传产物到 GitCode latest release | 本机 |

**版本号唯一来源：`package.json` 的 `version`。** 所有命令自动读它（拼成 `v<version>` 定位 release），正常流程**不需要传版本号**；`--tag <vX.Y.Z>` 仅作异常覆盖。唯一能显式定版本的是 `pnpm run release` / `release-all`（`--minor` / `--major` / `--version x.y.z`，默认 patch）。

## 3. 发版全流程

| 步骤 | 命令 | 说明 |
|---|---|---|
| 0. 一键全流程 | `pnpm run release-all` | **一条命令跑完 1-4**：自动 bump+push → 轮询 GitHub Actions 直到 CI 成功（默认超时 120 分钟，`RELEASE_CI_TIMEOUT_MS` 可调）→ 等 draft → Intel 本机自动 `pnpm build` + `--with-x64` 合并发布（arm64/其他平台只发布）→ 下载产物（Intel 机自动 `--skip mac-x64`，也支持手动 `--skip <平台>`）→ 同步 GitCode。`--dry-run` 只做前置检查；`--skip-build` / `--skip-mirror` 跳过对应步 |
| 1. 发版入口 | `pnpm run release` | 读最新 `v*` tag → 累加 → 写 package.json → commit `release: vX.Y.Z` → tag → push。拒绝 dirty 工作区 / 已存在 tag |
| 2. CI 三平台打包 | （自动） | tag push 触发 build.yml：macos-15(arm64)/windows/ubuntu 打包，electron-builder 建 **draft release**（`--publish onTagOrDraft`） |
| 3a. 仅发布（默认，任何机器） | `pnpm run publish-release` | 把 CI 建的 draft release 发布为公开，不做任何本地上传 |
| 3b. 本机补 mac 包（Intel 专属） | `pnpm build` → `pnpm run publish-release --with-x64` | **仅 Intel Mac 需要**：补发 x64 包 + 合并 latest-mac.yml + 校验 + 发布 |
| 4. 镜像 GitCode | `pnpm run download-release` → `pnpm run sync-domestic --dir release/mirror` | 下载全平台产物（本机已打过的平台用 `--skip` 复用本地副本）→ 一键上传 GitCode |

> **⚠️ draft 发布与 x64 补发解耦**：默认模式（不带任何参数）就是「仅发布」，不依赖本机是否 Intel——任何机器发完版都能把 release 转公开。`--with-x64`（Intel 本机）是可选的特殊情况，先补 x64 再发布。

## 4. 步骤详解

### 4.1 `pnpm run release`（版本累加 + 触发 CI）

- 自动读最新 `v*` tag，无参数默认 **patch**（`v0.1.2` → `v0.1.3`）；`--minor` → `v0.2.0`，`--major` → `v1.0.0`，`--version 0.3.0` 显式指定。
- 守卫：工作区不干净、目标 tag 已存在、无 origin 远端 → 拒绝执行。
- pnpm 会把脚本名后的参数原样转发，**不需要 `--` 分隔**。

### 4.2 CI（.github/workflows/build.yml）

- **只在 `v*` tag 推送时触发**（`on.push.tags`）；普通 push 不跑；`workflow_dispatch` 可手动。
- 三平台：macos-15（arm64）/ windows / ubuntu，各跑 lint → typecheck → install-engine → rebuild-engine → compile → smoke → build。
- tag 推送 → Package 步骤 `--publish onTagOrDraft`（建 draft release）；手动触发 → `--publish never`。
- mac 签名/公证凭据走 GitHub secrets（`CSC_LINK` / `APPLE_ID` 等），未配置时产物仅 ad-hoc 签名/未公证（打包不失败）。
- **镜像同步不在 CI 做**（GitHub runner → 华为云 OBS 实测不通），由本机 sync-domestic 维护。

### 4.3 mac 双架构与 `publish-release`

**为什么双架构要分开出**：引擎原生模块（`node-addon-require-builtin-*` / `@img/sharp-*` / `@koromix/koffi-*`）是 npm 平台变体包，npm 按 runner 架构只装匹配变体——arm64 runner 装不出 x64 变体，无法一个 runner 打双架构。

| 架构 | 谁出 | 产物 |
|---|---|---|
| arm64 | CI（macos-15） | `dsh-desktop-<v>-arm64.dmg` / `-arm64-mac.zip` |
| x64 | **本机 Intel Mac**（`pnpm build`） | `dsh-desktop-<v>-x64.dmg` / `-x64-mac.zip` |

`publish-release --with-x64`（Intel 本机）自动完成：计算本地产物 sha512/size → 以 `-x64` 后缀上传 → 合并 `latest-mac.yml`（arm64+x64 条目，electron-updater 按文件名匹配架构）→ 校验完整性 → 发布 draft。上传走 **HTTP/1.1**（Node fetch 的 HTTP/2 传大文件会 `ERR_HTTP2_STREAM_ERROR`）。

**默认模式（仅发布）**：不读本地产物、不传文件，只把 draft release 转公开——适用于任何机器（Apple Silicon 本机、或 CI 后先发布后补 x64）。x64 补发（`--with-x64`）是 Intel Mac 专属的特殊情况。

### 4.4 GitCode 镜像（手动下载 + 上传）

**`--from-github` 已移除**（2026-08）：国内直连拉 GitHub 大文件实测不可行（连接挂起），GitHub CI 上传华为云 OBS 也不通。唯一可行路径：

```sh
# 1. 用 gh CLI 下载 GitHub release 产物（dmg/zip/exe/AppImage/latest-*.yml，过滤 blockmap）
pnpm run download-release                 # 全量下载
pnpm run download-release --skip mac-x64  # 本机刚 pnpm build 过 x64：本地复制、跳过下载
                                          # 其他平台同理：--skip mac-arm64 / --skip win / --skip linux（可组合）
# 2. 上传到 GitCode latest release（原文件名）
pnpm run sync-domestic --dir release/mirror
```

**旧版本残留自动清理（两层，无需手工删）**：① `download-release` 下载/复制后删除 mirror 目录里非当前版本的 `dsh-desktop-*` 文件（如上版的 `Setup-0.1.3.exe`）；② `sync-domestic --dir` 上传前再按当前版本过滤一次——即使目录是手动放的，上一版产物也绝不会进 `latest` 镜像。`--skip` 复制的本地字节由 sync-domestic 的 sha512 校验对照 GitHub 的 latest-*.yml 把关。

`sync-domestic` 两种模式：
| 模式 | 命令 | 说明 |
|---|---|---|
| 本地直传 | `pnpm run sync-domestic` | 直传本机架构产物（Intel → x64，全自动） |
| 上传已下载产物 | `pnpm run sync-domestic --dir <path>` | 上传目录里原文件名的产物——完整镜像（arm64/win/linux）用这个 |

`sync-domestic` 流程：删旧附件（平台自动生成的源码归档 id 为 null 跳过）→ `GET upload_url` → 华为云 OBS 预签名 PUT（HTTP/1.1 + 重试）→ 校验附件齐全 + 匿名下载 latest-*.yml 逐字节比对。

**凭据**：`GITCODE_TOKEN`（.env.local）、`GITCODE_OWNER`/`GITCODE_REPO`（.env）。

## 5. 环境坑速查（发布相关）

- **mise 工具链**：`mise.toml` 里 pnpm 必须用 `"npm:pnpm"`（Intel Mac 上 aqua 后端不支持 darwin/x64）；node 下载慢 → 全局 config 配 `MISE_NODE_MIRROR_URL=https://npmmirror.com/mirrors/node/`。装好后 `node`/`pnpm` 走 mise shims；**`gh` 走 Homebrew**（`mise.toml` 未声明 gh，`~/.local/bin` 无 gh shim，实际是 `/usr/local/bin/gh` → Homebrew Cellar）。
- **gh 认证**：`gh auth status` 报 Bad credentials → 用新 read token 重新 `gh auth login --with-token`。**两个前提**：① 先 `unset GH_TOKEN GITHUB_TOKEN` 再执行——shell 里 export 着 token 时 gh 会拒绝存储凭据（`To have GitHub CLI store credentials instead, first clear the value from the environment`）；② 仅 export `GH_TOKEN` 不够：`download-release` 的守卫跑的是 `gh auth status`，要求 gh **存储的**凭据有效（本机曾出现 env token 有效但 stored 凭据过期、脚本仍报「gh 未登录」）。`.zshrc` 里的 `GITHUB_TOKEN` 若失效同样会污染 gh，注意同步更新。**不是每次发布都要重登**：stored 凭据存进 macOS keyring 后持久有效，`gh auth status` 不报错即可直接跳过；且只有 `download-release`（下载 GitHub 产物）依赖 gh，`release`/`publish-release`/`sync-domestic` 分别走 git 凭据、`.env.local` 的 `GH_TOKEN`、`GITCODE_TOKEN`，均不需要 gh。**v0.1.4+ 已加兜底**：`gh auth status` 失败但存在 `GH_TOKEN` 时，`download-release` 自动切换到隔离配置目录（`release/.ghcfg`）重试，stored 凭据失效不再阻塞发布流程。
- **`GH_REPO` 是仓库名，不是 `OWNER/REPO`**：`.env` 的 `GH_REPO=deepseek-harness-desktop` 是 electron-builder `${env.GH_REPO}` 宏所需格式；而 gh CLI 要求 `OWNER/REPO`（`GH_REPO` 环境变量存在时 gh 优先读它，仓库名会直接报 `expected the "[HOST/]OWNER/REPO" format`）。`download-release` 已自动处理（v0.1.6+，当前 main）：`GH_OWNER`+`GH_REPO` 齐全时拼 `--repo owner/repo` 显式传给 gh（`GH_REPO` 已含 `/` 则原样用），两者都缺失时退回 gh 从 git remote 推断。**不要**为了让 gh 工作而把 `.env` 的 `GH_REPO` 改成 `owner/repo`——会破坏 electron-builder 的 publish 宏。
- **`pnpm run download-release` 文件已存在报错**：脚本已加 `--clobber`，重跑会覆盖。
- **release 是 draft**：CI 默认建 draft；`pnpm run publish-release` 默认发布为公开；`--keep-draft` 可跳过。
- **`/releases/tags/<tag>` 对 draft 返回 404**：publish-release 已兼容（从 `/releases` 列表匹配 tag_name）。
- **大文件上传 HTTP/2 中断**：publish-release / sync-domestic 均走 HTTP/1.1（node:https）+ 重试。
- **下载的 mirror 文件可能不完整**（size 明显小于预期 = 中断残留，实测 arm64 zip 只有 10MB/应为 193MB）：重跑 `download-release`（`--clobber`）会覆盖；`sync-domestic --dir` 上传前会做 sha512 比对，坏文件会被拦下。

## 6. 用户侧更新行为

- GitHub 分发用户：electron-updater 读 `app-update.yml` → GitHub Releases。
- GitCode 分发用户：electron-updater generic provider → `.../releases/download/latest/`。
- 应用内 `auto` 模式：先探测 GitCode，失败降级 GitHub；可手动固定源（管理窗口「设置与更新」）。
- mac 更新依赖 zip（dmg 不能差分）；blockmap 做增量下载。
